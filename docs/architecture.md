# Архитектура

Модульный монолит: React-SPA (`apps/web`) и один сервис NestJS
(`apps/api`) на PostgreSQL. Правила, которые нужны и серверу, и
интерфейсу, — в общем пакете `packages/domain`.

## Модули

```
apps/web  ──HTTP /api──►  apps/api  ──Prisma──►  PostgreSQL
   │                          │
   └──────────┬───────────────┘
              ▼
       packages/domain  (автоматы, статусы, тексты, actions, правила полей)
```

**api** (`apps/api/src`):

| Где                      | Что                                                                      |
| ------------------------ | ------------------------------------------------------------------------ |
| `core/clock`             | `Clock` — единственный источник «сейчас», демо-сдвиг часов               |
| `core/access`            | метки маршрутов `@Public()`, `@Roles(…)`; без метки — только вошедшим    |
| `core/policies`          | права по таблице ТЗ 4.4 и сборка `actions[]`                             |
| `core/event-bus`         | доменные события после коммита транзакции                                |
| `core/errors`            | единый формат ошибок `{ code, message, fields? }`                        |
| `core/validation`        | общие правила текстовых полей DTO                                        |
| `core/prisma`            | клиент БД                                                                |
| `core/config`            | настройки стенда из окружения (`DEMO_MODE`, `STAND_ID`, интервал сброса) |
| `modules/auth`           | регистрация, вход, сессии, `GET /me`, настройки                          |
| `modules/events`         | создание, изменение, лента и поиск, карточка                             |
| `modules/participations` | запись, заявки и решения организатора, «Мои записи», лимит мест          |
| `modules/messages`       | обсуждение мероприятия                                                   |
| `modules/notifications`  | уведомления внутри платформы — обработчики доменных событий              |
| `modules/organizations`  | профиль организации, отправка на проверку, решение                       |
| `modules/sports`         | каталог направлений и подсказки                                          |
| `modules/admin`          | обзор, допуск организаций, модерация, каталог                            |
| `modules/demo`           | сид, сброс демо-данных, перемотка часов (только при `DEMO_MODE=true`)    |
| `modules/health`         | проверка готовности для Compose                                          |

Слои внутри модуля: контроллер (DTO, без логики) → сервис (политика,
переход автомата, сохранение, доменное событие) → репозиторий (Prisma).
К чужим данным модуль обращается через сервис другого модуля, а не через
его репозиторий.

**web** (`apps/web/src`): `features/<раздел>` — экраны и запросы раздела
(`feed`, `event-card`, `events`, `participations`, `discussion`,
`notifications`, `organizations`, `admin`, `auth`, `demo`, `check`,
`navigation` — каркас, шапка и нижняя панель);
`shared/` — дизайн-система (`ui`, `theme`), клиент api, часы стенда
(`useClock()`), иллюстрации.

## Модель данных

Схема — `apps/api/prisma/schema.prisma`, имена в БД — `snake_case`.

- `User` (роль `user` / `org` / `admin`), `Session`, `UserSport` — интересы.
- `Organization` — у владельца-аккаунта роли `org`; статус проверки,
  причина решения, `OrganizationSport`.
- `Sport` — каталог: группа (`SportCategory`), нормализованное имя и
  алиасы, признак пользовательского, статус `active` / `hidden`.
- `Event` — организатор-пользователь **или** организация, направление,
  время, место, режим записи `free` / `approval`, лимит мест, уровень,
  условия, «Информация для участников», статус и причина статуса.
- `Participation` — запись человека на мероприятие: статус, ответ на
  вопрос заявки, причина решения.
- `Message` — вопрос или ответ в обсуждении, от себя или от организации.
- `Notification`, `ModerationLog` — уведомления и журнал решений модератора.
- `AppState` — настройки стенда: сдвиг демо-часов, время последнего сброса.
- Таблицы P2 (`Helfigochi*`, `Accessory`, `UserAccessory`,
  `CalendarToken`, `SeriesSubscription`, `EventSeries`, `CompanyRequest`) уже в
  схеме; в интерфейсе не используются (при объединении направлений в каталоге
  их ссылки на направление переносятся).

Частичные уникальные индексы заданы в `schema.prisma` (`where: raw(…)`),
ограничения `CHECK` — ручной SQL-миграцией `*_constraints` в
`apps/api/prisma/migrations`. Тесты
ограничений идут на настоящей PostgreSQL (`npm run test:db`).

## Автоматы состояний

`packages/domain/src/state-machines` — переходы и их условия; сервис
выполняет только разрешённый автоматом переход, интерфейс по нему же
объясняет недоступные действия.

| Автомат     | Статусы                                                                       | Переходы                                                                                                                          |
| ----------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Мероприятие | `published`, `cancelled`, `unpublished`, `deleted`                            | публикация (начало в будущем), изменение и перенос до начала, отмена, снятие и удаление модератором, восстановление               |
| Запись      | `pending`, `confirmed`, `waitlist`, `rejected`, `cancelled`                   | запись (по заявке → `pending`, свободно → `confirmed` или `waitlist`), принять, отклонить, продвинуть из листа ожидания, отменить |
| Организация | `draft`, `pending`, `approved`, `rejected`, `needs_changes`                   | отправить на проверку; одобрить, отклонить, вернуть на правки — с причиной                                                        |
| Сообщение   | `visible`, `hidden_by_moderator`, `deleted_by_moderator`, `deleted_by_author` | скрыть и удалить модератором — с причиной, удалить автором                                                                        |

Статус карточки для человека (`displayStatus`: «Набор открыт», «Мест нет»,
«Идёт», «Завершено» и т. д.) вычисляется из статуса, времени `Clock` и
мест — `packages/domain/src/display-status.ts`.

## Демо-часы

- `Clock.now()` — синхронный; при `DEMO_MODE=true` к реальному времени
  прибавляется сдвиг из `AppState` своего стенда, кешированный в памяти
  процесса (поэтому на стенд — один процесс api).
- `POST /demo/clock` сдвигает часы вперёд, `POST /demo/reset` пересоздаёт
  демо-данные от текущего времени и обнуляет сдвиг.
- Каждый ответ api несёт `X-Server-Time`; web берёт «сейчас» из `useClock()`
  (время сервера плюс ход часов браузера), поэтому статусы и «через 2 дня»
  в интерфейсе совпадают с тем, что проверяет api.
- ESLint запрещает `Date.now()` и `new Date()` без аргументов вне
  реализации часов. Пояс пользователей — `Asia/Krasnoyarsk`, в БД и API —
  UTC.

## Политики и `actions[]`

- Функции `core/policies` (`canJoin`, `canLeave`, `canManageEvent`,
  `canSeeParticipantInfo`, `canPostMessage`, `canEditOrganization`,
  `canModerate`, …) возвращают решение с кодом отказа. Сервис по нему
  бросает ошибку, а `toAction()` превращает то же решение в элемент
  `actions[]` ответа: `{ code, enabled, reason?, reasonCode?, requiresAuth? }`.
- Интерфейс показывает кнопки только по `actions[]` и сам права не
  проверяет; неактивная кнопка показывает причину, гостю — вход с
  возвратом к действию.
- Сборщики: `eventActions` (карточка), `participationActions` (заявки у
  организатора), `organizationActions` (профиль и админка).

## Доменные события

Сервис публикует события (`ParticipationConfirmed`, `EventUnpublished`,
`OrganizationDecided`, …; перечень — `core/event-bus/events.ts`) через
`afterCommit`: обработчики получают их только после успешной транзакции.
Обработчики уведомлений идут асинхронно, их ошибка не ломает действие.
