# Тандем

Веб-приложение для совместных спортивных активностей (заказчик — Столото):
найти событие, понять условия и записаться, а если подходящего нет — создать
своё.

Модульный монолит в одном репозитории (npm workspaces):

| Каталог           | Что внутри                                                           |
| ----------------- | -------------------------------------------------------------------- |
| `apps/api`        | Backend на NestJS                                                    |
| `apps/web`        | Frontend на React + TypeScript + Vite                                |
| `packages/domain` | Общие правила фронтенда и бэкенда, собирается в CommonJS и ES-модуль |
| `e2e`             | Сквозные тесты Playwright                                            |

## Для кого

Для людей, которые хотят заниматься спортом вместе с другими: найти
занятие рядом и в своё время, понять условия и записаться — свободно или
по заявке. Для организаторов-людей и организаций, прошедших проверку, —
создать мероприятие, принимать заявки и отвечать на вопросы. Для
администратора — допуск организаций, модерация мероприятий и обсуждений,
каталог направлений.

## Стек и почему он

| Слой          | Выбор                                                           | Почему                                                                                                |
| ------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Frontend      | React 19, TypeScript, Vite, React Router, TanStack Query        | SPA с кешем запросов; темы «Крупный текст» и «Высокий контраст» — токены CSS без отдельной библиотеки |
| Backend       | Node.js, NestJS 11 (TypeScript), `class-validator`              | Модули, DTO с проверкой полей и guard'ы доступа из коробки; один сервис — модульный монолит           |

| Развёртывание | Docker Compose: `web` (nginx), `api`, `db`                      | Один `docker compose up` поднимает стенд с миграциями и демо-данными                                  |

Подробнее — [`docs/architecture.md`](docs/architecture.md).

## Зависимости

- Для запуска: Docker с Compose v2.
- Для разработки: Node.js 24 (`.nvmrc`) и npm, PostgreSQL 17 (или контейнер
  `db` из Compose).
- Основные пакеты: `@nestjs/*`, `prisma` и `@prisma/adapter-pg`,
  `class-validator` (пароли — argon2id из `node:crypto`, без отдельного пакета); `react`, `react-router`, `@tanstack/react-query`;
  `vitest`, `@playwright/test`; шрифты `@fontsource-variable/*`. Полный
  список и версии — `package.json` пакетов и `package-lock.json`.

## Запуск в Docker

Нужны Docker и Docker Compose.

```sh
docker compose up --build
```

- приложение — http://localhost:8080
- API — http://localhost:3000/health (через приложение — http://localhost:8080/api/health)

Порты меняются переменными `WEB_PORT` и `API_PORT`, например
`WEB_PORT=8081 docker compose up --build`. Web публикуется на всех адресах
компьютера; `WEB_BIND=127.0.0.1` оставляет его видимым только с этого компьютера
(так стенд поднимает CI). Api всегда публикуется только на `127.0.0.1`.

Другие переменные окружения api:

| Переменная                    | По умолчанию в Compose | Что делает                                                                                                       |
| ----------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `DEMO_MODE`                   | `true`                 | Быстрый вход, сброс и перемотка демо. На стенде без демо — `false` (в коде по умолчанию `false`)                 |
| `DEMO_RESET_INTERVAL_SECONDS` | `10`                   | Минимум секунд между сбросами демо-данных (повтор раньше — 429 с `Retry-After`). Для e2e — `0`                   |
| `STAND_ID`                    | пусто                  | Номер стенда (`stand-1` …): показывается в демо-панели и входит в имя cookie входа                               |
| `SESSION_SECRET`              | пусто                  | Секрет сессий стенда, не короче 32 символов. Пусто — создаётся при первом старте и хранится в томе `api-secrets` |
| `SESSION_COOKIE_SECURE`       | `false`                | `true` — cookie входа только по HTTPS (стенд с TLS)                                                              |

## Локальная разработка

Нужен Node.js 24.7 или новее (см. `.nvmrc`): пароли хешируются встроенным `crypto.argon2`.

```sh
npm ci
export SESSION_SECRET=$(node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))")
npm run build:domain              # общий пакет нужен api и web в собранном виде
npm run dev -w @tandem/api        # сборка API в режиме наблюдения
npm run start -w @tandem/api      # запуск API на http://localhost:3000
npm run dev -w @tandem/web        # фронтенд на http://localhost:5173, /api проксируется на API
```

API нужна PostgreSQL в `DATABASE_URL`. Её можно поднять отдельно:

```sh
docker run -d --name tandem-pg -p 127.0.0.1:5433:5432 \
  -e POSTGRES_USER=tandem -e POSTGRES_PASSWORD=tandem -e POSTGRES_DB=tandem postgres:17-alpine
export DATABASE_URL=postgresql://tandem:tandem@127.0.0.1:5433/tandem
npm run migrate:deploy -w @tandem/api
```

## База данных

Схема — `apps/api/prisma/schema.prisma`, миграции — `apps/api/prisma/migrations`.
В Docker Compose api применяет миграции сам при каждом старте.

- Изменить схему: правка `schema.prisma`, затем
  `npm run migrate:dev -w @tandem/api -- --name <что изменено>`.
- CHECK-ограничения (ровно один организатор, нормализованная почта, одна строка
  настроек стенда) Prisma не описывает: они в ручной миграции `*_constraints`.
- Частичные уникальные индексы (одна неотменённая запись на пару «событие —
  пользователь») заданы в схеме через `where`.

## Демо-данные

При `DEMO_MODE=true` api после миграций заполняет **пустую** базу демо-данными
(`node dist/seed.js`, он же `npm run seed -w @tandem/api` после сборки). Состав —
как в `docs/scenarios.md`: 8 демо-аккаунтов быстрого входа и 10 фоновых участников
(пароль у всех `demo`), организации в статусах для проверки сценариев, каталог из 25
направлений в 8 группах и пользовательский «Петанк», 10 мероприятий с составами,
заявками, «Информацией для участников» и обсуждениями. Базу с данными сид не трогает.

Даты относительные: от `Clock` по календарю Красноярска («послезавтра 8:00»,
«ближайшая среда 19:00» — не раньше чем через 3 часа, иначе через неделю), поэтому
в любой день мероприятия в правильном времени. Данные —
`apps/api/src/modules/demo/seed-data.ts` и `seed-events.ts`.

- `POST /demo/reset` стирает данные стенда и строит сид заново, обнуляет
  сдвиг демо-часов и запоминает время сброса (`lastResetAt` в `GET /clock`).
  Сессии тоже стираются: после сброса нужно войти снова. Сброс, начатый раньше,
  повторный запрос не запускает заново, а получает его результат; новый сброс —
  не раньше чем через `DEMO_RESET_INTERVAL_SECONDS` после прошлого (429 с
  `Retry-After`).
- `POST /demo/clock` с `{ "addSeconds": 3600 }` сдвигает демо-часы вперёд
  (до года); сдвиг хранится в базе своего стенда.
- Вне `DEMO_MODE=true` обе ручки отвечают 404.

## Демо-стенды

Сброс и перемотка демо-часов действуют на всю базу стенда. Поэтому для
проверки поднимаются три одинаковых стенда, по одному на проверяющего. Все
три берутся из одного `docker-compose.yml`, и каждый — отдельный проект Compose
со своей базой, своим секретом сессий и своими портами:

| Стенд     | Приложение | API (только на сервере) | Файл                 |
| --------- | ---------- | ----------------------- | -------------------- |
| `stand-1` | 8081       | 3001                    | `stands/stand-1.env` |
| `stand-2` | 8082       | 3002                    | `stands/stand-2.env` |
| `stand-3` | 8083       | 3003                    | `stands/stand-3.env` |

Порт API открыт только на `127.0.0.1` сервера; снаружи api доступен через
приложение: `http://<сервер>:8081/api/…`.

```sh
sh scripts/stands.sh up              # собрать и поднять все стенды
sh scripts/stands.sh up stand-2      # только один стенд
sh scripts/stands.sh ps              # состояние
sh scripts/stands.sh logs stand-1    # журнал стенда
sh scripts/stands.sh down            # остановить; данные стендов сохраняются в томах
```

- Номер стенда (`STAND_ID`) отдаёт `GET /clock` — его показывает демо-панель; он
  же входит в имя cookie входа, поэтому стенды на одном адресе не делят вход.
- Сдвиг демо-часов и время последнего сброса хранятся в базе своего стенда:
  `POST /demo/reset` и `POST /demo/clock` на одном стенде другие не трогают.
- Стереть данные стенда целиком (новый сид при следующем старте):
  `docker compose -f docker-compose.yml -p stand-1 --env-file stands/stand-1.env down -v`.

### Стенды на сервере команды

| Стенд     | Адрес                       |
| --------- | --------------------------- |
| `stand-1` | http://109.196.167.209:8081 |
| `stand-2` | http://109.196.167.209:8082 |
| `stand-3` | http://109.196.167.209:8083 |

Стенды открыты всем и работают по HTTP без шифрования: при регистрации на них не
вводите настоящие пароли и личные данные — для проверки есть демо-аккаунты.

Обновление — одной командой с компьютера, с которого есть вход на сервер по
SSH-ключу:

```sh
sh scripts/deploy.sh                          # свежий origin/prod на все стенды
DEPLOY_REF=<коммит> sh scripts/deploy.sh      # нужный коммит из истории prod, например откат
DEPLOY_RESET=1 sh scripts/deploy.sh           # и сбросить демо-данные — перед передачей экспертам
```

Выкатывается только коммит из истории `origin/prod`. Миграции идут только вперёд:
если откатываемый выпуск старше миграции, стенд пересоздают с чистой базой
(на сервере в `~/tandem/current`: `docker compose -p stand-N down -v`, затем выпуск —
демо-данные создаст сид).

Скрипт отправляет на сервер архив коммита (`git archive`: только файлы
репозитория, без `.env` и `.git`) в `~/tandem/releases/<коммит>`, переключает
`~/tandem/current` и запускает `sh scripts/stands.sh up`. Базы и секреты сессий
стендов — в томах Docker, обновление их не трогает; миграции применяются при
старте api. В конце скрипт проверяет `/api/health` и номер стенда в `/api/clock`
и при сбое печатает журнал стенда. Сервер и пользователь — переменная
`DEPLOY_HOST`. Настройки стендов — только `stands/stand-N.env` (в git, без
секретов); корневой `.env` стенды не читают.

## Ядро API

Общие части api — в `apps/api/src/core`; модули пользуются только ими.

- **Время — только из `Clock`** (`core/clock`). `Clock.now()` синхронный.
  При `DEMO_MODE=true` к нему прибавляется сдвиг демо-часов из таблицы
  `app_state` своего стенда, вне демо-режима сдвиг не применяется. Сдвиг
  кешируется в памяти процесса и загружается до приёма запросов, поэтому на
  стенд — **один процесс api**. После записи сдвига или сброса демо-данных
  вызовите `clock.refresh()`. Каждый ответ несёт заголовок `X-Server-Time`,
  `GET /clock` отдаёт `{ now, demoMode, standId, lastResetAt }`. ESLint
  запрещает `Date.now()` и `new Date()` без аргументов везде, кроме
  `core/clock` в api и `shared/clock` в web (хук `useClock()`).
- **Ошибки** (`core/errors`) приходят как `{ code, message, fields? }`.
  `code` — из закрытого списка `ERROR_CODES` в `@tandem/domain`, там же
  тексты; HTTP-код задаёт `ERROR_HTTP_STATUS`. В сервисе бросайте
  `new ApiError('event_not_joinable')`; отказы автоматов, ошибки DTO и
  нарушения уникальности фильтр переводит сам. Тексты ошибок полей DTO
  пишутся в декораторах `class-validator` по-русски.
- **Доменные события** (`core/event-bus`): полный перечень —
  `events.ts`. Публикуйте через `eventBus.afterCommit(async (emit) =>
prisma.$transaction(…))`, тогда события уйдут только после коммита.
  Обработчик — метод с `@OnDomainEvent('ParticipationConfirmed')`; он идёт
  асинхронно, его ошибка попадает в журнал и не ломает действие.
- **Права** (`core/policies`): функции по таблице ТЗ 4.4 (`canJoin`,
  `canManageEvent`, `canSeeParticipantInfo`, …) возвращают решение с кодом
  отказа. Сервис по нему бросает ошибку, а `toAction()` превращает его в
  элемент `actions[]` ответа. Пример — `eventActions()` для карточки события.
- **Вход** (`modules/auth`): `POST /auth/register`, `/auth/login`,
  `/auth/demo-login` (только при `DEMO_MODE=true`, ключ из `DEMO_ACCOUNTS`
  в `@tandem/domain`), `/auth/logout`, `GET /me`. Сессия — cookie
  `tandem_session[_<STAND_ID>]`. Глобальный guard кладёт в запрос `actor`;
  в контроллере его берёт `@CurrentActor()`. **Маршрут без метки доступен
  только вошедшим**; открытый всем помечается `@Public()`, доступ ролям —
  `@Roles('user', 'org')` (гостю — 401, чужой роли — 403); метки — из
  `core/access`. Пароли — argon2id; учётки `*@demo` вне демо-режима не входят.
  Попытки входа и регистрации ограничены по адресу и по почте (429 с
  `Retry-After`); вычислений argon2 одновременно не больше двух. Лимит по
  почте засчитывает любые попытки: десять неверных паролей закрывают вход в
  этот аккаунт на 10 минут. Порт api опубликован только на `127.0.0.1` —
  адрес клиента api берёт из `X-Forwarded-For`, который ставит web.
- **Изменяющие запросы** (POST, PUT, PATCH, DELETE) принимаются только со
  страниц своего стенда (`Sec-Fetch-Site` или `Origin`) и с телом в JSON —
  обычная форма с чужого сайта получает 403 или 415 до маршрута.

## Проверки

```sh
npm run lint        # ESLint и Prettier
npm run typecheck   # TypeScript в строгом режиме во всех пакетах
npm test            # unit-тесты Vitest
npm run build       # сборка всех пакетов
```

Тесты ограничений базы идут на настоящей PostgreSQL. Каждый прогон создаёт
на сервере из `TEST_DATABASE_URL` свою временную базу, а после удаляет её.
Существующие базы тесты не трогают.

```sh
TEST_DATABASE_URL=postgresql://tandem:tandem@127.0.0.1:5433/tandem npm run test:db
```

Сквозные тесты идут против запущенного приложения:

```sh
WEB_BIND=127.0.0.1 DEMO_RESET_INTERVAL_SECONDS=0 docker compose up --build -d --wait
npx playwright install chromium   # один раз
npm run e2e                       # адрес меняется переменной BASE_URL
```

Для прогона нужен стенд с `DEMO_RESET_INTERVAL_SECONDS=0`: тесты сбрасывают данные
перед каждым тестом, а с интервалом получили бы 429. Такой стенд — с входом без
пароля и сбросом без интервала — публикуется только на `127.0.0.1` (`WEB_BIND`):
из сети его быть не должно видно. Стенды `scripts/stands.sh` для этого не подходят:
у них интервал задан в `stands/stand-N.env`, а ни одна переменная, которую читает
`docker-compose.yml`, и ни `COMPOSE_FILE` из shell на них не действуют, чтобы
оставшиеся после e2e `0` и `127.0.0.1` не сняли защиту сброса с открытых стендов и
не закрыли их для экспертов.

Стенд должен быть в демо-режиме (`DEMO_MODE=true`, в Compose так по умолчанию):
перед каждым тестом его демо-данные сбрасываются. Поэтому тесты идут в один поток
и **стирают данные стенда** — не запускайте их против стенда, на котором кто-то
работает. Тест берёт `test` и `expect` из `e2e/support/fixtures.ts`, а под
демо-аккаунтом входит через `loginAs('anna')` (ключи — `DEMO_ACCOUNTS` в
`@tandem/domain`). Быстрый вход лимитом попыток не ограничен, а вход по паролю и регистрация ограничены по адресу (в памяти api, сброс демо-данных их не обнуляет): сценарии с регистрацией в одном прогоне с одного адреса упрутся в лимит регистраций. Трейс и скриншот упавшего теста — в `e2e/test-results`, отчёт —
в `e2e/playwright-report`; в CI они прикладываются к заданию `e2e`.

Те же lint, типы, тесты, тесты базы, запуск compose и сквозные тесты выполняются в GitHub Actions на каждый
PR в `prod` и push в `prod`.

## Как проверить

- На стенде страница **«Как проверить»** (`/check`): сценарии 1–6 и
  проверки P1 маршрутом «роль → действие → ожидаемый результат», кнопки
  входа под нужным демо-аккаунтом и ссылки на нужные экраны, список
  стендов. Подробные шаги — [`docs/scenarios.md`](docs/scenarios.md) (на
  стенде — `/check/scenarios`).
- Перед проверкой — «Сбросить демо-данные» в демо-панели: сценарии
  независимы. Демо-панель (видна только при `DEMO_MODE=true`) — номер стенда,
  время последнего сброса, перемотка часов «+1 час», «+1 день», «Завершить
  это событие».
- Демо-доступы: быстрый вход на экране входа и на `/check`; почта
  `<ключ>@demo`, пароль у всех — `demo` (аккаунты и их роли — в
  [`docs/scenarios.md`](docs/scenarios.md)).
- Сценарии прогоняют e2e-тесты Playwright (`e2e/tests/scenario-*.spec.ts`).

## Правила доступа и модерации

- Гость видит ленту, карточки опубликованных мероприятий, обсуждения и
  публичные страницы одобренных организаций; любое действие — после входа с
  возвратом к нему.
- Пользователь записывается и подаёт заявки, создаёт мероприятия от себя,
  пишет в обсуждения. «Информация для участников» видна только
  подтверждённым участникам, организатору и администратору.
- Организация создаёт мероприятия только после одобрения администратором:
  профиль → проверка → решение («одобрена», «отклонена», «нужны правки» — с
  причиной).
- Администратор снимает с публикации и удаляет мероприятия, скрывает и
  удаляет сообщения — всегда с причиной, которую видят организатор и
  записавшиеся; решения — в журнале модерации. Снятое мероприятие пропадает
  из ленты и поиска, записаться на него нельзя (409).
- Права проверяет сервер (политики `core/policies`); интерфейс показывает
  кнопки по `actions[]` из ответа и сам права не решает.

статусом, местами и главной кнопкой; запись свободно и по заявке, «Мои
записи»; создание и изменение мероприятия; обсуждение с вопросами и
ответами, метка «Организатор»; уведомления внутри платформы; контур
организации (профиль, проверка, публичная страница); админка (обзор, допуск
организаций, модерация мероприятий и сообщений, каталог направлений); темы
«Крупный текст» и «Высокий контраст»; демо-стенды, демо-панель, «Как
проверить».

**Имитируется и упрощено:** время — демо-часами (`Clock` со сдвигом, только
при `DEMO_MODE=true`); время показывается в поясе Красноярска; демо-данные
пересоздаются кнопкой сброса; вход — почтой и паролем, без подтверждения почты
и восстановления пароля; уведомления — только внутри платформы, без почты и
пушей; обсуждение обновляется раз в 30 секунд, без доставки в реальном
времени; оплаты нет — цена мероприятия только показывается; внешние сервисы
не используются; стенды — по одному Compose-проекту на стенд (см.
«Демо-стенды»).

**Известные ограничения:** проверки P1 3.1–3.5 (условия участия целиком,
лист ожидания и лимит мест полностью, отмена и перенос события с
уведомлениями, частые вопросы из обсуждения) сделаны не полностью — см.
«Как проверить»; P2 (карта OpenStreetMap, Хелфигочи, рекомендации,
календарь, серии встреч) не реализованы, хотя часть таблиц уже есть в
схеме; допуск одобренной организации отозвать нельзя; у организатора нет
экрана «Мои мероприятия» — свои мероприятия он находит в ленте и по
уведомлениям.
